# FLUX 跟踪数据并行采集方案说明

## 1. 目标

用多机多 GPU 并行生成 tracking 训练数据（stt / dt / at 三种模式）。
每个 Isaac Sim 进程占用 **1 张 GPU**，串行消费分配给它的场景切片；
多张 GPU 同时跑多个独立进程，从而并行加速。

- 单进程单卡，稳定优先（不在一个 GPU 上叠多个 Isaac 进程，避免 OOM）
- **每 GPU 严格串行**：每个 GPU 起一个后台 subshell，内部逐 scene
  串行（等上一个 `test_mode_gen.sh` 退出再起下一个）。因此**任意时刻
  每张卡同时只有 1 个 Isaac 进程**，绝不会像早期那样一卡并发几十个
  容器互相抢卡
- 支持 **resume**：已处理过（accept 或 reject）的 episode 自动跳过，重跑不浪费 GPU 时间
- 失败 episode（带 `_REJECTED`）自动移到 `rejected/` 子目录，防误用

## 2. 脚本与数据流

```
logs_formal_v3/
├── run_distributed.sh         # 并行驱动器：切片场景 + 每 GPU 起串行 subshell
├── test_mode_gen.sh          # 单实例采集：选 episode → 跑 docker → 边渲染 → quarantine
├── _render_videos.py        # png → mp4（调试用，非训练数据）
└── formal_runs/             # 正式产物根目录
    ├── launch_logs/          # 所有运行日志集中于此（不再散落根目录）
    │   ├── run_<ts>.log          # 每次 run_distributed 的总摘要（场景分配等）
    │   └── launch_gpu<g>.log     # 每个 GPU 的串行进度日志
    └── <short_scene>/            # ← 直接用短 scene ID，无前缀、无内层 scene 嵌套
        ├── run_info.txt
        ├── stt|dt|at/<ep>/<robot>_<camera>/    # ← 无内层 scene 文件夹
        │       rgb/ depth/ *.png      # ← 训练数据（png 保留）
        │       rgb_video.mp4 depth_video.mp4   # ← 仅调试
        │       _ACCEPTED | _REJECTED    # ← 质量标记
        │       0_info.json 0.json quality.json camera_info.json track_object.jpg
        ├── rejected/<mode>/<ep>/<combo>/       # ← 无内层 scene 文件夹
        ├── tmp_episodes/<mode>/<scene>/episode_*.json  # 中间输入
        └── logs/<mode>/<combo>/_container.log + _render.log  # ← 无内层 scene 文件夹
```

> **目录名直接用短 scene ID（如 `0001_83992`），无 `formal__` 前缀、无内层
> scene 文件夹**。scene ID 截掉末位以缩短目录名（`0001_839920` → `0001_83992`），
> 不影响内部使用完整 ID 进行数据查找和 resume。resume 以 `scene + mode + combo`
> 为粒度检查标记，因此**同一 scene 换 GPU、或迁移到另一台机器重跑，都能命中
> 已有标记并跳过**，不会因为换了卡前缀而重复计算。

`run_distributed.sh` 仅为驱动器：它把 `[SCENE_START, SCENE_END)` 的场景
**round-robin 分配给各 GPU**，每个 GPU 起一个串行 subshell。真正的数据
逻辑都在 `test_mode_gen.sh`。

## 3. 场景与规模

- 场景源：`/mnt/ssd1/zeyingg/SAGE-3D_Official/SAGE-3D_data/v3_tracking_episodes/`
- 场景总数：**987**（全局索引 0..986，由 `sage_utils/episode_caches/*.json` 排序决定）
- 每个场景：stt/dt/at 三种模式，每模式最多 100 个 episode
- 单 episode 实测耗时（max_steps=300 量级）：约 3–4 分钟（含 Isaac 启动 ~30s）
- 默认每模式采 **10** episode，每场景组合 = 3 模式 × 6 combo(robot×camera) × 10 = **180 episode**

总任务量（全量 987 场景）：约 **177,660 episode**。

## 4. 关键参数（传给 run_distributed.sh）

| 变量 | 默认 | 含义 |
|------|------|------|
| `SCENE_START` | 0 | 场景全局索引起点（含） |
| `SCENE_END` | 2 | 场景全局索引终点（不含） |
| `GPU_IDS` | `"0 1"` | 本机参与采集的 GPU 列表（空格分隔） |
| `ROBOT_TYPES` | `"go2 g1 dingo"` | robot 组合（combo 维度） |
| `CAMERA_TYPES` | `"realsense_d435i zed"` | camera 组合（combo 维度） |
| `TRACKING_MODE` | `all` | `stt` / `dt` / `at` / `all` |
| `MAX_EPISODES` | 10 | 每模式最多采多少 episode |
| `MAX_STEPS` | 300 | 单 episode 最大步数 |

> 以上变量名请**原样复制**，与脚本内部读取名一致。
> （脚本内部变量拼写以仓库实际代码为准，复制本文件命令即可。）

场景切片方式：把 `[SCENE_START, SCENE_END)` 的场景列表 **round-robin**
分配给 `GPU_IDS` 里的各卡。例如 2 卡、范围 [0,2)：
GPU0 拿 scene0，GPU1 拿 scene1。每张卡串行跑完它分到的所有场景。

## 5. 单机执行命令

> **重要：用 detached 后台方式运行**，不要前台阻塞终端。
> 所有日志自动写到 `formal_runs/launch_logs/`（`run_<ts>.log` 总摘要 +
> `launch_gpu<g>.log` 每卡进度），**不要再手动 `> m6_xxx.log` 散落根目录**。
> 变量值含空格时必须加引号（`ROBOT_TYPES="go2 g1 dingo"`），漏引号会导致
> shell 把 robot 名当成命令执行报 `g1: command not found`。

## 6. 多机分工（machine4 / machine5 / machine6）

按 GPU 数比例切分场景索引段，每台机子**独立**运行、产物落各自
`formal_runs/`，互不干扰，可随时启停、可迁移。

| 机器 | GPU 数 | 场景索引段 | 场景数 |
|------|--------|------------|--------|
| machine6（本机） | 4 | 0 – 357 | 358 |
| machine4 | 4 | 358 – 715 | 358 |
| machine5 | 3 | 715 – 987 | 272 |

各机命令（仅 `SCENE_START/END` 与 `GPU_IDS` 不同），统一 detached 运行：

```bash
# 在每台机器上分别执行（screen 中运行）
cd /mnt/nvme1/zeyingg/FLUX/logs_formal_v3

# machine6 (4 GPU)
env SCENE_START=0   SCENE_END=357 GPU_IDS="0 1 2 3" \
  ROBOT_TYPES="go2 g1 dingo" CAMERA_TYPES="realsense_d435i zed" \
  MAX_EPISODES=10 MAX_STEPS=300 \
  bash run_distributed.sh > formal_runs/m6_scene0_357_v2.log 2>&1

# machine4 (4 GPU)
env SCENE_START=358 SCENE_END=715 GPU_IDS="0 1 2 3" \
  ROBOT_TYPES="go2 g1 dingo" CAMERA_TYPES="realsense_d435i zed" \
  MAX_EPISODES=10 MAX_STEPS=300 \
  bash run_distributed.sh > formal_runs/m4_scene358_715_v1.log 2>&1

# machine5 (3 GPU)
env SCENE_START=715 SCENE_END=987 GPU_IDS="0 1 2" \
  ROBOT_TYPES="go2 g1 dingo" CAMERA_TYPES="realsense_d435i zed" \
  MAX_EPISODES=10 MAX_STEPS=300 \
  bash run_distributed.sh > formal_runs/m5_scene715_987_v1.log 2>&1
```

> 三台机子场景段互不重叠，产物目录都叫 `formal__<short_scene>`，**合并时
> 直接按 short scene 名对齐即可**，不会因为某机换了 GPU 前缀而冲突或重复。

若某机新增 / 减少 GPU，只需改该机的 `GPU_IDS` 列表，
场景段按 GPU 总数重新均分即可。

## 7. Resume（断点续采）

`test_mode_gen.sh` 在每个 combo 启动前，检查它要生成的所有 episode
目录是否都已存在 `_ACCEPTED` **或** `_REJECTED` 标记：

- 两者任一存在 → 视为"已处理"，**跳过，不启动 docker**
- 因此重跑同一条命令会自动续采，已完成的绝不重复计算
- **rejected 的 episode 不会重跑**（再跑大概率仍 reject，避免浪费 GPU）
- **resume 与 GPU 无关**：因为产物目录是 `formal__<short_scene>`（不含 gpu
  前缀），哪怕把某 scene 换到另一张卡、甚至迁到另一台机器重跑，标记
  依然命中并跳过。这是 round-robin 切片 + scene-only 命名的设计红利。

直接重跑 5.x 的同一条命令即可续采，无需手动记录进度。

> 注意：resume 以 `(scene + mode + combo)` 为粒度。
> 若改变了 `MAX_EPISODES` / `ROBOT_TYPES` / `CAMERA_TYPES` /
> `TRACKING_MODE` 等，会产生新的 combo 维度，旧标记不会覆盖新组合
> （这是期望行为：新组合本就该跑）。

## 8. 耗时估算（基准：单 episode ≈ 3–4 min @ max_steps=300）

单 GPU 吞吐 ≈ 15–20 episode/小时 ≈ 360–480 episode/天。

| 配置 | GPU 数 | 每天 episode | 全量 177,660 ep 耗时 |
|------|--------|------------|---------------------------|
| 单机 machine6 | 4 | ~1,600–1,900 | ~95–110 天 |
| 三机并行 | 11 | ~4,400–5,300 | **~34–40 天** |

若只采部分场景：

| 场景数 | 11 GPU 耗时 |
|--------|-------------|
| 100 | ~7–8 天 |
| 200 | ~15 天 |
| 358（machine6 全段） | ~26–30 天 |

> 实测单 episode 在 max_steps=600 时约 6.5 min；降到 300 步后
> 约 3–4 min。实际会更快，因为并非所有场景三种模式都满 100
> episode（扫描结果显示部分场景仅某一模式有数据）。

## 9. 产物与后续

- **训练数据**：每个 episode 的 `rgb/`、`depth/` 下 png（保留，不删）
- **调试视频**：`rgb_video.mp4` / `depth_video.mp4`（仅人眼检查用）
- **质量标记**：`_ACCEPTED`（可用）/ `_REJECTED`（已隔离到 `rejected/`）
- **合并多机产物**：把各机的 `formal_runs/formal__<short_scene>/` 按目录结构
  直接合并；剔除所有 `rejected/` 子目录即可得干净训练集
- **日志**：`formal_runs/formal__<scene>/run_info.txt` 记录
  每个 combo 的 OK / WARN / SKIP(resume) 状态；
  运行级日志见 `formal_runs/launch_logs/`

## 10. 迁移到其他机子的前置条件

1. 代码已提交 `linker/dev`，其他机子 `git pull` 即可拿到
   `run_distributed.sh` + `test_mode_gen.sh` + `_render_videos.py`
   + `tracking_episode_collection_datagen.py`
2. `sage_utils/episode_caches/` 需存在（987 个 json）；缺哪个
   `test_mode_gen.sh` 会在 Phase 1 自动 `pre_scan_scene.py` 补扫
3. docker 镜像 `quay.io/zeyinggong/flux:v2_deploy` 各机需可拉取
4. `SAGE3D_DIR`（默认 `/mnt/ssd1/zeyingg/SAGE-3D_Official`）
   若其他机子路径不同，需在脚本顶部改该环境变量
5. 容器以 root 写盘后会在退出前 `chown` 归还宿主机当前用户，
   故各机直接用自己账号跑即可，无需 sudo
